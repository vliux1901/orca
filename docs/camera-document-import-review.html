Import flow proposal

Let users scan paper maintenance documents without creating a second import system.

The proposal keeps Orca's current document-import model intact: the user still ends with one ordered document import per vehicle, stored locally and then queued for extraction. The change is the source of those files. In addition to picker-based imports, Orca should offer a scan path optimized for receipts, invoices, and printed service paperwork, with JPEG pages as the first scanner output format.

Primary goal Add a paper-document path that feels native and low-friction for receipts and service paperwork.
Flow shape Keep the existing vehicle-targeting and repository flow, then branch only at source acquisition.
Reuse target Reuse PendingImportSource, SourceImportRequest, and the existing repository/extraction pipeline.
Product tradeoff Prefer one guided scanner path over exposing raw camera capture first, because paper documents usually need edge detection, multi-page flow, and scan-specific preview.

Current documentation gap

Conflict to resolve before implementation: the current PRD still lists Camera capture as out of scope for V1 and also says the current product decision is file upload only. This proposal intentionally changes that product boundary. It should not be implemented silently without updating the PRD and technical design after review.

Proposal principles

  • Scanning a paper receipt should not require the user to first save photos into their gallery.
  • The import entry points should stay visible where they already exist: vehicle detail, vehicle list, and onboarding.
  • The app should keep one shared import pipeline after acquisition so testing, storage, extraction, and error messaging stay consistent.
  • When a platform or device cannot support the preferred scanner flow, Orca should fall back to a simpler camera-capture path rather than dead-ending the user.

Technical Design

The cleanest implementation is to treat scanning as another source-acquisition strategy that produces ordered JPEG page files, then hand those files to the current import/repository pipeline. The UI work is larger than the storage work.

Architecture direction Extract a shared import controller from the three current entry points so vehicle detail, vehicle list, and onboarding stop each owning their own picker and review state. Camera support will otherwise triple the launcher and error-handling work.
Primary scanner recommendation Use ML Kit's Android document scanner as the first-choice paper flow. It already provides a dedicated viewfinder, preview UI, multi-page scanning, and can return JPEG page URIs through Activity Result APIs. Orca should treat those JPEG page files as the canonical first implementation.
Fallback strategy If scanner startup fails or the device is unsupported, fall back to a simpler TakePicture-style capture contract backed by an app-owned temporary file URI.
Storage rule Keep storing final imported sources only through DocumentRepository.importDocument(). Temporary capture files should live outside the document store and be cleaned up after import or cancellation.

Proposed app flow

  1. User taps an existing Import Document CTA.
  2. If needed, Orca asks which vehicle will own the import.
  3. Orca opens a shared source-method chooser with Choose existing files and Scan paper document.
  4. File imports continue through OpenMultipleDocuments() and the current ImportImageReviewDialog.
  5. Paper scans launch the scanner flow and return ordered JPEG page URIs or a fallback camera capture URI.
  6. Orca converts the returned pages into SourceImportRequest objects, imports them, queues extraction, and navigates to document detail.

Concrete code changes

  • Add a shared import-flow owner in [VehicleHubCommonUi.kt](/home/vliux/code/orca/app/src/main/java/org/vliux/orca/ui/vehicle/VehicleHubCommonUi.kt) or a nearby import-specific file so the three screens stop duplicating launcher state.
  • Introduce a small sealed model such as ImportAcquisitionMethod with at least FILES, SCAN_DOCUMENT, and internal fallback CAMERA_CAPTURE.
  • Extend PendingImportSource in [ImportImageReview.kt](/home/vliux/code/orca/app/src/main/java/org/vliux/orca/ui/vehicle/ImportImageReview.kt) so it can represent scanner-origin pages and optionally carry a cleanup callback for temporary files.
  • Add a temp-file helper, preferably injected through Hilt, that creates and later deletes app-private capture files. This fits the repo's existing dependency style better than ad hoc file handling inside a composable.
  • Use SourceImportRequest.markConsumed() to trigger temp-file cleanup after DocumentRepository finishes or fails, instead of leaving capture files behind.
  • Add a new shared UI surface that replaces the current file-only guidance dialog with a method chooser containing short import education plus scanner/file actions.

Scanner implementation detail

Preferred path Configure ML Kit document scanner for JPEG page output first. That maps naturally onto Orca's existing ordered-source model and image-preview UI, and it is the explicit recommended format over PNG for the first release.
Why not PDF first A scanner-generated PDF is possible, but JPEG pages align better with today's document-detail thumbnail grid, page ordering, and image-based inspection flow. PNG is not the preferred default because scanned paper is photographic content and JPEG keeps storage and upload cost lower. PDF output can remain a later option if retention needs change.
Review behavior Skip Orca's current rotate-confirm loop for scanner-origin pages because the scanner SDK already provides preview and retake. Re-running both reviews would feel redundant.
Fallback behavior If the scanner path cannot start, drop into a manual capture loop backed by ActivityResultContracts.TakePicture, then send the captured image through Orca's existing review dialog before import.

Testing plan

  • Unit-test the new import-method routing so each entry point chooses the same shared flow.
  • Unit-test temp-file cleanup for cancel, success, and repository-failure paths.
  • UI-test the chooser surface, fallback messaging, and scanner-unavailable path using fake launchers or adapter interfaces rather than binding tests directly to Play-services UI.
  • Keep the current image-review tests for picker-based imports and add coverage proving scanner-origin images bypass duplicate review.
  • Run the existing import-related build, unit, and lint verification after product code changes, since this feature touches shared vehicle-import UI.

Recommended Rollout

Phase 1: Refactor the shared import flow Move picker state, image-review state, and common success/error handling into one reusable import-flow owner without changing behavior yet.
Phase 2: Add source-method chooser Replace the current file-only pre-picker dialog with a chooser that supports both file import and paper scan.
Phase 3: Integrate scanner path Add the preferred document-scanner SDK path and transform returned pages into SourceImportRequest objects.
Phase 4: Add fallback capture path Handle unsupported devices or scanner-start failures with a simpler manual photo capture path.

Open risks and decisions

Product wording The current import guidance copy is file-centric. It needs to be rewritten so Don't show again does not hide the only path explanation for paper scans.
Unsupported-device UX The primary scanner path has device constraints. Orca needs a friendly fallback message instead of a raw exception.
Duplicate-page artifacts If multiple result formats are enabled for one scan, the app will create duplicate logical sources. The first implementation should pick one canonical output format: JPEG pages.
UI duplication risk If the code is not refactored first, the same scanner logic will be duplicated across three screens and become expensive to maintain.
