Scope

This document defines the V1 local persistence schema for the Android app described in docs/technical-design.html. It covers Room entities, storage paths, relationships, and rules for persisting cloud-extracted maintenance data.

  • Use Room as the authoritative local database.
  • Store original imported image and PDF files in app-private storage.
  • Treat one logical maintenance document as a container that may include multiple imported source files.
  • Persist raw extraction metadata needed for retries, review, citations, and audit, but not raw provider prompts or responses.

Design Principles

  • Schema should preserve source provenance from logical document to specific imported file to cited page or file segment.
  • User corrections should supersede extracted values without destroying the original extraction record.
  • Status transitions should be explicit so imports, extraction runs, and user edits can recover safely after app restarts.

File Layout

The database stores metadata only. Binary source files stay in app-private storage and are referenced by stable relative paths from document_sources.

files/vehicles/{vehicleId}/documents/{documentId}/sources/source-001.{ext}
files/vehicles/{vehicleId}/documents/{documentId}/sources/source-002.{ext}
files/vehicles/{vehicleId}/documents/{documentId}/sources/source-003.{ext}
  • vehicleId is the owning vehicle UUID.
  • documentId is the logical document UUID.
  • source-00N preserves source ordering inside one logical document.

File Metadata Rules

  • Store file size, mime type, display name, and checksum in the database for duplicate detection and troubleshooting.
  • Keep a relative file path rather than an absolute device path so backup/restore and app-private relocation remain possible.
  • Do not assume one page per file. A PDF source may contain multiple pages; an image source usually maps to one page-equivalent input.

Table Summary

  • vehicles: vehicle identity and optional profile fields used to group maintenance records.
  • documents: one logical maintenance document and its processing lifecycle.
  • document_sources: one imported image or PDF file, ordered within a document.
  • extraction_runs: one provider/model attempt against a logical document.
  • document_facts: extracted or user-corrected facts with citations.
  • maintenance_events: normalized service events shown on the timeline.
  • service_items: itemized maintenance work attached to an event, with optional per-item cost.
  • search_entries: flattened search rows derived from facts, events, and evidence snippets.

Core Room Shapes

@Entity(tableName = "documents")
data class DocumentEntity(
    @PrimaryKey val documentId: String,
    val vehicleId: String,
    val title: String?,
    val sourceCount: Int,
    val importStatus: String,
    val extractionStatus: String,
    val latestRunId: String?,
    val occurredAt: String?,
    val createdAt: Instant,
    val updatedAt: Instant,
)

@Entity(
    tableName = "document_sources",
    foreignKeys = [
        ForeignKey(
            entity = DocumentEntity::class,
            parentColumns = ["documentId"],
            childColumns = ["documentId"],
            onDelete = ForeignKey.CASCADE,
        ),
    ],
    indices = [Index("documentId", "sourceOrder", unique = true)]
)
data class DocumentSourceEntity(
    @PrimaryKey val sourceId: String,
    val documentId: String,
    val sourceOrder: Int,
    val fileName: String,
    val mimeType: String,
    val relativePath: String,
    val byteSize: Long,
    val checksumSha256: String?,
    val pageCount: Int?,
    val createdAt: Instant,
)

sourceCount on documents is denormalized for fast list rendering and should always match the actual number of child rows. Room persists audit timestamps as ISO-8601 UTC text through converters while the Kotlin model surface uses Instant.

Status And Integrity Rules

  • documents.importStatus should move through pending, ready, or failed.
  • documents.extractionStatus should move through not_started, queued, running, succeeded, or failed.
  • A successful extraction run may create facts and derived timeline rows in one transaction.
  • User edits create a new active fact and mark the replaced extracted fact inactive rather than updating history in place.
  • Deleting a document cascades to sources, extraction runs, facts, events, service items, and search entries.

Indexes And Queries

  • Document list queries need indexes on vehicleId, updatedAt, and extraction status.
  • Timeline queries need an index on maintenance_events(vehicleId, eventDate).
  • Source review screens need document_sources(documentId, sourceOrder).
  • Fact review and replacement flows need document_facts(documentId, factType, isActive).

Cost Rules

  • maintenance_events.totalCostMinor stores the whole-document total when available.
  • service_items.costMinor stores an item-level amount when the document provides line-item pricing.
  • service_items.currencyCode should usually match the parent event currency, but stays nullable so partial item pricing does not block persistence.

Privacy Rules

  • Do not store raw provider prompts or raw provider responses in the database in V1.
  • Do not index filenames, VINs, license plates, or user questions into diagnostic logs.
  • If a later privacy mode adds local-model support, the schema should remain stable so backend choice changes only the extraction-run metadata, not the document model.

DAO Boundaries

  • VehicleDao: vehicle list and profile updates.
  • DocumentDao: document list, detail aggregate queries, insert/delete, and status updates.
  • ExtractionRunDao: enqueue, retry, and status updates.
  • FactDao: active fact queries, replacement writes, and citation lookups.
  • TimelineDao: event and service item reads for the maintenance timeline.

Migration And Test Cases

  • Add Room schema export and migration tests from version 1 onward.
  • Test multi-file imports, duplicate source ordering, cascade delete, failed extraction retries, and user fact replacement.
  • Use fixture databases for digital PDFs, scanned PDFs, receipts, rotated images, and mixed multi-file documents.
