Goal

This plan sequences implementation of the Android app defined in docs/prd.html, docs/technical-design.html, docs/database-schema.html, and docs/api-definition.html. The target is a V1 that imports maintenance PDFs/images, sends original source files to a cloud vision model, persists extracted facts with citations, builds a maintenance timeline, supports user correction, and answers simple factual queries.

  • Build vertical slices in dependency order rather than all UI first or all backend first.
  • Keep cloud-provider integration behind app-owned interfaces from the first implementation.
  • Do not add local-model privacy mode in V1 implementation.

Execution Strategy

  1. Establish project skeleton, persistence, and test harness first.
  2. Implement import and document storage before any cloud calls.
  3. Implement extraction as a background worker with fixture-driven validation before wiring full UI flows.
  4. Add timeline, corrections, and search after canonical facts persist reliably.
  5. Add simple factual QA last, because it depends on stable facts, citations, and search indexing.

Phase 0: Foundation

  • Audit the current Android project structure, dependency versions, and existing prototype code.
  • Add baseline modules or packages for UI, data, worker, provider adapter, and test fixtures if they do not already exist.
  • Set up Room schema export, WorkManager, Kotlin serialization, and OkHttp dependencies.
  • Define app configuration for provider base URL, model name, and auth source without hardcoding them into UI code.

Exit criteria: the app builds, Room schema export works, WorkManager can run a no-op worker, and configuration injection exists for provider access.

Phase 1: Persistence And File Storage

  • Implement Room entities, DAOs, and repositories for vehicles, documents, document sources, extraction runs, facts, maintenance events, service items, and search entries.
  • Implement app-private file copy logic for imported image/PDF files and persist document_sources.relativePath.
  • Implement multi-file logical document creation in one transaction.
  • Implement delete flows that cascade file cleanup and DB cleanup safely.

Exit criteria: a document with multiple source files can be created, listed, observed, and deleted with deterministic DB and file-state tests.

Phase 2: Import UI And Document Surfaces

  • Build vehicle list and vehicle detail entry points.
  • Build file-picker based import flow for image/PDF selection.
  • Build document list and document detail screens with status, source-file list, and placeholder extracted sections.
  • Queue extraction work after a successful import, with image-based imports first passing the required per-image review and rotation-confirmation step.

Exit criteria: a user can create a vehicle, import one or more files into a logical document, and see the queued document in the UI.

Phase 3: Cloud Extraction Pipeline

  • Implement MaintenanceExtractionEngine, ExtractionRequest, and the cloud adapter boundary.
  • Implement provider request building for original image/PDF source files plus prompt instructions about upright orientation and structural reconstruction.
  • Implement strict JSON parsing, schema validation, and error classification for malformed or partial responses.
  • Persist ExtractionRunEntity, extracted facts, interpreted shorthand expansions, and citations in one worker pipeline.
  • Handle retryable failures, terminal failures, and visible status updates for the document.

Exit criteria: fixture-backed worker tests pass, and a real provider integration can process a sample document end-to-end into stored facts.

Phase 4: Normalization, Timeline, And Search

  • Implement local normalization for dates, mileage, cost, vendor labels, and categories.
  • Implement a review-safe interpretation layer for dealer abbreviations and maintenance package codes that preserves raw text, citations, and confidence.
  • Derive one MaintenanceEventEntity per logical document in the normal V1 path.
  • Persist optional item-level pricing on ServiceItemEntity when the provider returns it reliably.
  • Implement delete-and-rebuild indexing for SearchEntryEntity on extraction success and correction updates.

Exit criteria: document detail shows extracted facts and service items, the timeline is populated, and search entries regenerate deterministically from canonical records.

Phase 5: Review And Correction

  • Build document detail review UI showing unverified facts, citations, raw dealer text, interpreted shorthand, and source-file list.
  • Implement user correction flows for service date, mileage, vendor, service items, and cost.
  • Implement replacement-fact writes so original extracted values remain in history and corrected values become active.
  • Trigger event rebuild and search-index rebuild after corrections.

Exit criteria: user corrections update the effective timeline and search results without destroying extraction history.

Phase 6: Vehicle Summary Views

  • Build the Vehicle Detail maintenance summary table from normalized maintenance_events and service_items, showing the most recent known maintenance row per vehicle component.
  • Add the repository and query support needed for that table so the UI can observe a vehicle-scoped derived summary without re-parsing document detail state in Compose.
  • Humanize normalized component categories for display while preserving the canonical stored category values underneath.

Exit criteria: Vehicle Detail shows the latest-known maintenance row per component and updates correctly as normalized events or service items change.

Phase 7: Search And Simple QA

  • Build keyword search over SearchEntryEntity.
  • Build simple factual QA over stored facts, events, service items, and citations.
  • Return concise answers, dates, mileage, and uncertainty notes when records conflict or are incomplete.
  • Keep V1 QA deterministic where possible and do not expand into open-ended recommendation behavior.

Exit criteria: supported factual questions return grounded answers with citations and explicit uncertainty.

Phase 8: Release Hardening

  • Add provider timeout, retry, and offline handling polish.
  • Add privacy disclosure, cloud-processing disclosure, and failure messaging in the UI.
  • Tune import/extraction UX for large PDFs and multi-file documents.
  • Run regression pass on representative fixtures and real sample docs.

Exit criteria: release candidate meets core flows, quality checks, and documented V1 scope boundaries.

Verification Strategy

  • Run build on every product-code change.
  • Add or update unit tests for every behavior change.
  • Run all related tests for each change set.
  • Keep fixture coverage for digital PDFs, scanned PDFs, receipts, rotated images, and multi-file logical documents.

Phase-Aligned Tests

  • Persistence tests: schema migration, DAO relations, transaction boundaries, cascade delete, and file-reference integrity.
  • Worker tests: request assembly, error classification, retry policy, JSON validation, and DB persistence.
  • Normalization tests: date parsing, mileage normalization, currency normalization, and category mapping.
  • Indexing tests: delete-and-rebuild search generation after extraction and correction.
  • UI tests: import flow, status transitions, detail review, shorthand interpretation display, and correction flow.

End-To-End Definition

Create vehicle
  -> import multi-file document
  -> files copied to private storage
  -> document and source rows persisted
  -> extraction worker runs
  -> cloud provider returns JSON
  -> app validates and saves facts
  -> event and service items derived
  -> search entries rebuilt
  -> document detail shows unverified facts and citations
  -> user corrects one field
  -> active facts, timeline, and search update

Decisions Needed Before Phase 3

  • Which cloud provider and model will be used for V1.
  • Whether provider calls go directly from device to vendor API or through an app-owned backend/proxy.
  • How provider credentials are issued and rotated.
  • Whether all pages/files are always sent or whether the user can choose subsets.

Decisions That Can Wait

  • Local-model privacy mode implementation.
  • Local PDF rasterization fallback.
  • Cloud-drive or email imports.
  • Richer question answering beyond factual retrieval.

Main Risks

  • Provider auth and secret management can block integration if deferred too long.
  • Real document variation may break prompt assumptions or strict JSON parsing.
  • Large PDFs and multi-file documents may create latency, request-size, or cost problems.
  • Correction flows can drift from canonical fact logic if event rebuild and search rebuild are not centralized.
  • Search and QA can become inconsistent if they bypass canonical facts and query provider output directly.

Risk Mitigations

  • Resolve provider, auth, and request-shape decisions before coding the extraction worker.
  • Build fixture-driven extraction validation before broad UI polish.
  • Keep event building and search rebuilding inside shared domain services.
  • Test against real messy samples early, not only clean invoices.
