First-run UX concept

Replace the empty vehicle list with a guided four-step new-user wizard.

This flow gets a first-time user from zero context to a useful setup state: understand the app, add at least one vehicle, optionally connect their OpenAI key with clear local-storage and authentication messaging, and optionally import the first maintenance documents.

Primary goal Reduce blank-screen friction and guide the user toward their first successful import.
Flow shape 4 screens, linear progression, with step 3 and step 4 explicitly skippable.
Visual direction Plain language, one clear main action per screen, and phone-sized cards that read like product screenshots.
Exit state End on the real vehicle hub with the user either partially configured or fully ready to import and extract records.
1. Welcome
2. Create vehicle profiles
3. Add OpenAI API key
4. Import vehicle documents

Flow Snapshot

Step 1 Set context and reassure the user that Orca is a personal maintenance-record organizer.
Step 2 Push the user directly into the create-vehicle action because that unlocks almost every later workflow.
Step 3 Explain third-party AI use, why the API key is user-supplied, and why device auth appears only when needed.
Step 4 Show import only after the user saves an API key; skipping the key should end onboarding instead.

Suggested transition behavior: after step 2, the wizard should remember whether at least one vehicle exists. If the user skips step 3, onboarding should end immediately. If the user reaches step 4 or exits during step 3, the app should not show the wizard again on every launch once the first-run state has been acknowledged.

Implementation Notes And Product Fit

Design principles

  • The wizard should feel like a guided setup, not a hard gate. Only vehicle creation is truly essential for useful app structure.
  • Step 3 should be recoverable later from the existing app surfaces, and step 4 should remain reachable after API key setup, so skipping does not strand the user.
  • Security and AI-use language should be explicit but short: local encrypted storage, third-party AI for analysis, and device auth only when a protected action needs the key.
  • Document import should preserve the existing guidance about multiple images or PDFs and the fact that originals stay local.

Implementation note

The implemented direction is to keep one secure API-key storage flow while exposing it from two entry points: first-run onboarding and the existing Settings screen.

Likely follow-up decisions

  • Should step 2 open the full create-vehicle form inline, or navigate into the existing vehicle-create screen and return to the wizard afterward?
  • Should step 3 use the exact current Settings copy and storage/auth logic so the onboarding screen is only a different entry point?
  • Should step 4 allow import without a configured API key and leave the document in a queued-but-not-configured state, matching the existing scheduler behavior?
