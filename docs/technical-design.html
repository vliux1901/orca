Purpose

This document designs the V1 Android app from docs/prd.html: an Android app for organizing car maintenance documents, extracting key facts, showing a maintenance timeline, and answering simple factual questions from the user's records.

The key design change from earlier iterations is this: V1 is cloud vision AI first, V1 is not local OCR first, and local model execution is a later privacy-mode option.

The reason is product quality. Local OCR-first processing loses too much structure before extraction, especially for receipts, scanned invoices, tables, and messy photos.

V1 Boundaries

Supported

  • Multiple vehicle profiles
  • Manual import of PDFs and images
  • Maintenance and repair documents only
  • Cloud vision AI extraction from document images or PDF pages
  • Unverified extracted facts, timeline, search, and simple factual QA

Not supported

  • Email, cloud-drive, dealer, manufacturer, or background sync imports
  • Non-maintenance vehicle documents
  • Local on-device model execution in V1
  • Local OCR-first extraction as the primary processing path

Design Principles

  • Optimize for extraction quality over cheapest processing.
  • Preserve source documents locally even when cloud extraction is used.
  • Treat cloud AI as a provider behind app-owned interfaces.
  • Keep extracted facts unverified until the user confirms or corrects them.
  • Validate and normalize all AI output locally before saving.

Architecture Summary

  • UI: Compose screens for vehicles, import, documents, timeline, edit, and ask/search.
  • ViewModel: screen state and command handling.
  • Repository: local DB plus app-private file storage.
  • Processing: source-file preparation, cloud vision extraction, validation, normalization, event building, and indexing.
  • AI provider layer: request building, transport, retries, and response parsing.

Primary V1 Flow

User imports PDF/image
  -> app copies one or more source files to private storage
  -> document row is created with status = queued
  -> source rows are created in import order
  -> worker sends original source files to cloud vision AI
  -> AI returns strict structured JSON plus evidence snippets
  -> app validates and normalizes extracted fields locally
  -> facts and citations are persisted as extracted_unverified
  -> maintenance event is built from preferred facts
  -> search index is rebuilt
  -> timeline shows unverified extracted result
  -> user corrections create verified replacement values

Future privacy mode keeps the same processing contract and only swaps the backend from cloud vision to local vision.

Dependencies

  • Use WorkManager for background processing.
  • Use Room for persistence.
  • Use Kotlin serialization for strict JSON parsing.
  • Use OkHttp or equivalent for provider transport.
  • Keep V1 simple: send original source files directly and defer local PDF rasterization unless later testing justifies it.

Storage Model

Use local app-private storage for source documents. Source documents stay local even when original image and PDF files are sent to a cloud AI provider for extraction.

files/vehicles/{vehicleId}/documents/{documentId}/sources/source-001.{ext}
files/vehicles/{vehicleId}/documents/{documentId}/sources/source-002.{ext}
files/vehicles/{vehicleId}/documents/{documentId}/sources/source-003.{ext}

One logical document may contain multiple imported image and PDF files. Those source files are stored separately under sources/ in document order.

In V1, the app sends original source files to the provider directly instead of generating local page-image artifacts first.

Core Tables

  • documents: one logical maintenance document, processing mode, and status.
  • document_sources: one imported file per row, with stable ordering inside the logical document.
  • extraction_runs: backend, model, prompt version, status, and retry history.
  • document_facts: extracted or corrected facts with citations and evidence snippets.
  • maintenance_events and service_items: timeline model.
  • search_entries: derived search rows from facts, events, and evidence.

Data Rules

  • Do not overwrite wrong extraction values. User edits create replacement facts.
  • Keep page number and evidence text with extracted facts for citation and review.
  • When receipts contain vendor shorthand such as package codes or abbreviations, store the raw extracted text separately from any AI-generated interpretation.
  • Do not log raw prompts, responses, VIN, license plate, filenames, service notes, or user questions.

Source-File Handling

  • Images: keep the original imported image file and send it directly to the provider.
  • PDFs: keep the original imported PDF file and send it directly to the provider.
  • This is the V1 choice because it is the simplest path and avoids premature tuning of local PDF rasterization parameters.
  • Local PDF rasterization can be added later if testing shows a clear quality benefit.

Provider Boundary

interface MaintenanceExtractionEngine {
    suspend fun extract(
        document: DocumentEntity,
        sources: List<DocumentSourceEntity>,
    ): ExtractionResult
}

The rest of the app should not care whether extraction came from a cloud provider or a future local vision model.

Prompt And Response Contract

  • Prompt the model to mentally rotate the input upright before extraction when needed.
  • Prompt the model to preserve structural meaning, reconstruct tables conservatively, and return strict JSON only.
  • Require source-file reference, page number, and short evidence snippets for each extracted field.
  • Allow the model to propose a plain-language interpretation for abbreviations or dealer codes, but require it to keep the original raw text and mark the interpretation as inferred.
  • Reject malformed JSON and locally validate dates, mileage, costs, and categories before persistence.

Validation And Timeline

  • Reject malformed JSON and impossible values.
  • Normalize currency, dates, and categories locally.
  • Treat dealer-code interpretations as secondary derived facts; they can inform review UI and search, but should not silently replace the raw extracted line item.
  • Build one maintenance event per document in most V1 cases.
  • Keep all extracted facts and timeline values marked unverified until corrected or confirmed.

UI And Error Handling

  • Show processing status per document.
  • Show source-file list, extracted facts, raw dealer text, AI interpretations, and unverified markers.
  • In document detail, prioritize service items directly below the summary. Keep source files, extracted facts, and timeline event in collapsed review sections by default, and let each service item reveal its linked raw line item on demand.
  • Disclose when cloud AI was used to process a document.
  • Fail safely on provider errors, malformed responses, render failures, and unsupported file types.

Testing And Milestones

  • Test normalization, malformed JSON rejection, conflicting values, event building, and deterministic QA.
  • Use fixture tests for digital invoices, scanned invoices, receipts, rotated images, and multi-file logical documents.
  • Milestone 2 centers on cloud vision extraction and timeline creation.
  • Milestone 4 introduces privacy mode with a local backend behind the same interface.

Risks And Open Decisions

  • Cloud AI raises privacy, cost, and latency concerns.
  • AI may still misread values, so local validation and user correction stay mandatory.
  • Open decisions include provider/model choice, page resizing policy, selected-pages versus all-pages sending, encryption needs, and backup behavior.
